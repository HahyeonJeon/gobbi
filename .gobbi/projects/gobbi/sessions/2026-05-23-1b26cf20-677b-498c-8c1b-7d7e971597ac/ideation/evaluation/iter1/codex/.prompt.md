## 4-Stage Evaluation Procedure

Run all 4 stages sequentially. Never skip a stage.

### Stage 0 — Target Understanding

1. Read the artifact END TO END. Do not skim.
2. Identify artifact type: `ideation` (scope-contract + framed problem + research insights + scenarios + implementation checklist + design).
3. Phase tag: `ideation`. Load seed scenarios from `/playinganalytics/git/gobbi/.claude/skills/ideation/evaluation.md`.
4. **W/W/H gate**:
   - What: the concrete deliverable (T1 worktree-first architecture + T3 PostToolUse hook + reconstructor)
   - Why: the trigger / root cause (session artifacts leaking to wrong tree; `agents[]` empirically unpopulated)
   - How: directional design decisions (D-1 through D-5, D-3-1 through D-3-4)
   - If What or Why is missing/ambiguous: record Critical `general` finding (domain: `unevaluable`), halt Stage 0.
   - If How is missing: record Critical `general` finding (domain: `unevaluable`), continue best-effort.
5. **Phase-mismatch gate**: Confirm artifact type == `ideation`. If diverges, halt and record.
6. Read ALL project mistakes listed above — filter by relevance to each perspective.
7. Run file-existence checks on key claims: Does `git/SKILL.md` exist? Does `.claude/hooks/session-start.sh` exist? Does `session.template.json` exist? Does the `1829fa3` commit cited exist in git log?
8. Write Artifact Summary (one paragraph): What / Why / How / Scope Contract source / downstream consumers.

### Stage 1 — Scenario-Checklist Frame Build (per perspective)

For each of the 7 perspectives in order (Project → Structure → Performance → Aesthetics → Usage → Consistency → Risk):

1. Filter the artifact's scenarios to those relevant to this perspective.
2. Load seed scenarios from the ideation phase child doc for this perspective.
3. CRUD on scenarios: CREATE missing adversarial scenarios, UPDATE ambiguous ones, DELETE OOS. Every Create/Update emits a `scenario_gap` finding.
4. Attach checklists to each scenario. CRUD on checklist items. Every Create/Update emits a `checklist_gap` finding.
5. Write the **Locked Frame** under `## Locked Frame (Stage 1)` header in each perspective file.

**Adversarial requirement**: each perspective's Frame MUST include ≥1 adversarial scenario OR explicit `not-applicable: <rationale>`.

### Stage 2 — Per-Perspective Sequential Evaluation

Perspectives in order: Project → Structure → Performance → Aesthetics → Usage → Consistency → Risk.

For each perspective:
1. Walk each scenario and its attached checklist. Judge each check item yes/no with specific evidence.
2. Use bash commands (grep, find, cat) to verify file-existence and code-pattern claims in the artifact — DO NOT reason about existence, verify it.
3. Surface unanticipated findings as typed findings. Do NOT suppress to fit the Frame.
4. Tag every finding: Type + Domain + Confidence + Severity + Evidence + `surfaced-by: codex` + `disposition: open`.
5. FP-check before assigning confidence ≥50.
6. Compute verdict: any Critical confidence≥75 → FAIL; any High confidence≥50 → REVISE; otherwise PASS.

**Verdict line format**: each file MUST end with a line: `Verdict: PASS` / `Verdict: REVISE` / `Verdict: FAIL`

### Stage 3 — Overall

1. Identify cross-perspective tensions in per-perspective verdicts.
2. Identify cross-cutting findings no single perspective owns.
3. Check all 4 **Karpathy failure modes** explicitly:
   - **Wrong assumptions**: premises in Framed Problem that research doesn't support
   - **Overcomplexity**: design that could have used an existing pattern
   - **Orthogonal edits**: Scope Contract bundles unrelated concerns
   - **Imperative-over-declarative**: evaluation criteria prescribe mechanism vs verifiable goal
4. List strengths to preserve.
5. Compute Overall verdict (same threshold rules).

## Finding Metadata Schema

Every finding MUST carry ALL of:
```
- type: <scenario_gap|checklist_gap|design_flaw|assumption_risk|general>
- domain: <security|performance|test|observability|privacy|compliance|dependency|docs-sync|cost|accessibility|i18n|unevaluable|phase-mismatch|regression|process|general>
- confidence: <0|25|50|75|100>
- severity: <Critical|High|Medium|Low>
- evidence: <quote or file:line or tool output>
- surfaced-by: codex
- disposition: open
```

**5-Type vocabulary** (use verbatim in frontmatter `type:` field):
- `scenario_gap` — missing scenario
- `checklist_gap` — missing checklist item
- `design_flaw` — concrete flaw (broken invariant, wrong abstraction, missed failure mode)
- `assumption_risk` — assumption that may not hold
- `general` — does not fit above (use sparingly)
