## Typed findings
- **ST-1 — T1 is a heavyweight materialization task (~64 real files) folded as one category.** Type: design_flaw. Domain: process. Disposition: open. Confidence: 50. Severity: Low. Evidence: T1 `files:` includes `plugins/gobbi/skills/**` (18 dirs, each multi-file — canonical tree is 57+ real files per skills-mirror-symlinks-not-copies.md) + 5 agents + 2 hooks; 5-clause verifies (a-e). Why it matters: it exceeds the child-doc "≤5-8 files" smell, but the mechanism (a sync script that produces all copies in one run) makes splitting artificial — splitting "write script" from "run script" would split one commit/category. Suggested direction: acceptable as-is; the executor should commit the script and its generated output together. No action required beyond awareness.
- **ST-2 — T5 and T6 `verifies:` are not autonomously runnable by a spawned executor subagent.** Type: assumption_risk. Domain: process. Disposition: open. Confidence: 75. Severity: Medium. Evidence: T5 verifies requires "Install the plugin... into a clean installed-only environment with NO active in-repo .claude/settings.json dev registrations; run...; assert the marker log contains EXACTLY one line per hook_event_name... PostToolUseFailure triggered by a Task engineered to exit non-zero." T6 verifies requires invoking `gobbi:codex` etc. "post-install" inside a live session. A subagent executor cannot (a) spawn a fresh interactive Claude session, (b) temporarily disable the live `.claude/settings.json` dev hooks (this dev session IS using them), (c) dispatch a deliberately-failing Task tool call and read hook markers. Why it matters: the plan presents these as task verifications, but they are operator-in-the-loop procedures requiring a human-driven install + a separate clean Claude session. If the Execution manager hands T5/T6 to an executor expecting an autonomous pass/fail, the verification will stall or be faked (cf. mistake reproducing-a-bugged-command-is-not-validation + leader-iter2-verification-claim-without-evidence). Suggested direction: the plan should mark T5/T6 verification as operator-assisted (manager/user runs the install + clean session; executor authors the scripts + assert harness). This is a structural gap in *who runs the check*, not in the check's correctness. Note: this is the single most important finding in the evaluation — flag for user discussion.
