## 1. The packaging path

**Electron Forge is the path Electron's own tutorial uses, exclusively.** That is the whole of the claim.
No Electron page declares Forge recommended *over* electron-builder by name, and the code-signing
documentation lists electron-builder among the tools it covers
(`verified-against the electronjs.org documentation on 2026-07-26`). electron-builder is a maintained,
widely used alternative; nothing in this skill says otherwise, and a reviewer should not read a preference
for Forge as a defect in a project that ships with electron-builder.

Pick one and let it own the whole pipeline. **The failure to avoid is mixing the two toolchains' halves** —
packaging with one and updating with the other. Each pairs its packager with its own updater and its own
artifact and metadata layout: Forge's makers and publishers feed `update-electron-app`, electron-builder's
targets feed `electron-updater` and the `latest.yml` family it writes. A mixed pipeline packages
successfully and produces an update feed the client cannot read, which is a failure that surfaces on a
user's machine at the first release, not in CI.

The build order is the same either way, and every later section here is one step of it:

```text
compile the three targets  →  copy into the app bundle  →  pack app.asar (+ --unpack)
  →  flip the fuses  →  code sign  →  notarize (macOS)  →  make installers  →  publish
```

Two steps in that order are load-bearing rather than conventional: fuses are flipped **before** signing
(§ 3), and notarization happens **after** signing on an already-signed artifact (§ 4).

## 2. What goes into the artifact, and what ASAR is not

The packager copies the built `main`, `preload` and `renderer` output into the app bundle and packs it into
`app.asar`, a concatenated archive with a header. It is a packaging format: it keeps thousands of small
files off the user's disk as files, and it gives `embeddedAsarIntegrityValidation` something to validate.

**Two things it is not.**

- **Not a security or secret boundary (EL-N-06).** `original-fs` is Electron's ASAR-unaware `fs`, and it
  reads straight through the archive; anything inside is recoverable by anyone holding the app. The
  vendor's own description of the archive's `fs.stat` results is that they are
  *"generated by guessing"* — the header carries what it carries, not a real stat. A secret in the bundle
  is a published secret whether or not it is packed.
- **Not a load path for native code.** A `.node` binary cannot be loaded from inside the archive; the
  vendor lists the APIs that need a real file path and gives `--unpack` as the answer. This is why a native
  dependency that works in development fails at first launch of a packaged build with an error naming a
  path inside `app.asar`.

```text
asar pack app app.asar --unpack *.node
```

Either toolchain wraps that option — Forge under `packagerConfig.asar.unpack`, electron-builder under
`asarUnpack`; take the glob syntax from the tool you use. Unpacked content lands in `app.asar.unpacked/`
beside the archive and is **not** covered by the ASAR integrity fuse. Unpack the native binaries and
nothing else: every extra pattern moves a file out from behind the integrity check for no gain.

For secrets, keep them out of the artifact entirely. `safeStorage` encrypts at rest on the user's machine
and has its own Linux caveat, owned by [`windows-native.md`](windows-native.md).

## 3. Flipping the fuses, before signing

Fuses are boolean flags written **into the Electron binary** of the packaged app. [`security.md`](security.md)
owns which fuses and why. This section owns three things it does not: where the flip sits in the build, how
it is written, and what the verification has to read.

**The flip happens at packaging time, after the app is packed and before code signing.** Both halves of that
sentence matter. Before packaging there is no binary to modify; after signing, modifying the binary
invalidates the signature that was just applied, so the app ships with a broken signature — on macOS it will
refuse to launch, which at least fails loudly, and on Windows it fails the SmartScreen check that the
certificate was bought to satisfy.

Either toolchain gives the flip a hook — Forge's `@electron-forge/plugin-fuses` (recorded at 7.11.2) wraps
it, and electron-builder's `afterPack` hook calls it directly. Both call the same function:

```text
import { flipFuses, FuseVersion, FuseV1Options } from '@electron/fuses';

await flipFuses(pathToPackagedElectronBinary, {
  version: FuseVersion.V1,
  strictlyRequireAllFuses: true,
  resetAdHocDarwinSignature: targetPlatform === 'darwin' && targetArch === 'arm64',
  [FuseV1Options.RunAsNode]: false,
  [FuseV1Options.EnableNodeOptionsEnvironmentVariable]: false,
  [FuseV1Options.EnableNodeCliInspectArguments]: false,
  [FuseV1Options.GrantFileProtocolExtraPrivileges]: false,
  [FuseV1Options.EnableEmbeddedAsarIntegrityValidation]: true,
  [FuseV1Options.OnlyLoadAppFromAsar]: true,
});
```

Three options in that block are not decoration.

- **`strictlyRequireAllFuses: true`** hard-fails the build when the Electron binary being packaged carries a
  fuse this config says nothing about — a new fuse in a new major, or an old one someone dropped from the
  object. Without it, an unconfigured fuse takes its default silently, so the posture degrades across an
  upgrade with a green build. This is the same class of failure as scoring a read-back only over the fuses
  the tool happened to report (EL-R-12), moved to the write side.
- **`resetAdHocDarwinSignature`** is required for `arm64` macOS builds *when the flip is not immediately
  followed by code signing*; the modified binary otherwise fails Apple Silicon's code-signature validation
  and the app refuses to launch. In a pipeline that signs right after flipping, real signing supersedes it.
- **`GrantFileProtocolExtraPrivileges: false`** is the one whose Electron default is `true`. Leaving it out
  of the object leaves the privilege on.

**Verification is a read-back from the shipped artifact, not from the build config.** The config states an
intent; the read states what shipped, and the two diverge exactly when a hook silently did not run.

```text
npx @electron/fuses read --app <path-to-signed-artifact>
```

`UNVERIFIED-AGAINST-ARTIFACT`: this invocation is transcribed from the `@electron/fuses` README
(`verified-against that README on 2026-07-26`) and has not been run against a packaged build here, because
this project produces none. The first packaged build clears the marker.

Read it back **on every platform and architecture that ships**, and compare against the posture entry by
entry. A posture entry the read does not report is a **failure**, not a match. The two ways a green result
lies: one architecture was read and the other shipped unflipped, and the comparison was scored over the
tool's output rather than over the intended posture. Both produce a clean line in a build log.

## 4. Code signing and notarization

Signing is not only a distribution formality. It gates runtime behavior: macOS notifications require a
code-signed application (since 42, `migration.md`), and an unsigned build's deep links and installer flows
differ from the shipped one. A property proven on an unsigned local build is proven in a runtime nobody
ships (SKILL.md principle 8).

**macOS — sign *and* notarize. They are two steps.** Signing applies your Developer ID certificate to the
bundle; notarization uploads the signed artifact to Apple, which scans it and returns a ticket that is then
stapled to the artifact. A signed but un-notarized app is blocked by Gatekeeper on first launch on a
machine that has never seen it, which is every user's machine. `@electron/notarize` (recorded at 3.1.1) is
the step's tool and both toolchains have a hook for it.

**Windows — an EV or cloud-HSM certificate, since June 2023.** The certificate authority requirements
changed that month: private keys for code-signing certificates must be held in hardware or a certified
cloud HSM, so a downloadable `.pfx` file no longer satisfies SmartScreen reputation. A build pipeline
carrying a `.pfx` in a secret store is signing with a certificate class that no longer earns the
reputation it was bought for. Plan for a signing service the CI job calls, not a file it downloads.

Linux packages are not signed in the same sense; distribution-specific repository signing is out of this
skill's scope.

**Order:** flip fuses (§ 3) → sign → notarize → staple → make installers. Anything that modifies the binary
after signing invalidates the signature, which includes a fuse flip, a rebuilt native module, and a
post-processing step that rewrites the bundle.

## 5. Native modules

A native module is compiled against a specific ABI. Electron does not use the system Node's ABI: it embeds
its own Node version and its own `NODE_MODULE_VERSION`, so a module built by `npm install` against the
developer's Node is built for the wrong runtime. The symptom is a launch-time error naming a mismatched
`NODE_MODULE_VERSION`, and it is a **build-environment** error, not a code error.

**Never fix it by changing the Node version (EL-N-07).** Matching the system Node to Electron's embedded
Node produces a binary that loads on the machine where the versions happened to align and fails on every
other, including every user's. Two correct fixes:

- **`@electron/rebuild`** (recorded at 4.2.0) rebuilds the module against the Electron ABI of the version
  the app targets. Both toolchains run it as part of packaging; run it in CI too, not only locally.
- **An N-API module**, whose ABI is stable across both Node and Electron majors. Prefer it when the choice
  is open: the cost it avoids is a forced rebuild on every Electron major upgrade, not a size or speed
  difference (SKILL.md judgment default).

`npm rebuild` is the trap in the middle. It names no Node-version change, it succeeds on the developer's
machine, and it rebuilds against system Node — a green local result and a broken shipped app.

**C++20 is the floor since Electron 33.** V8 and Node both require it upstream, so a native module still
building with `--std=c++17` fails to compile; images on gcc9 or lower need gcc10 or newer
(`migration.md` carries the row). Cross-compiling for a different architecture needs that architecture's
toolchain — a rebuild does not follow from a successful `x64` build.

## 6. Auto-update: the evidenced part

**An update channel is a code-execution path.** It downloads a binary and runs it on the user's machine
with the user's privileges. Every obligation in § 3 and § 4 applies to what it delivers, not only to what
you hand-install: an update artifact is packaged, fuse-flipped, signed and notarized exactly like the
initial download, and both platforms enforce it — an unsigned macOS update fails Gatekeeper, and Windows
update flows check the signature. An update feed served over anything but HTTPS, or from a host you do not
control, hands that execution path to whoever does.

Two packages exist for this, each belonging to one toolchain's half (§ 1): `update-electron-app` (recorded
at 3.3.0) and `electron-updater` (recorded at 6.8.9).

**The mechanism is deliberately not taught here.** Feed-URL shape, differential updates, staged rollout and
channel selection are not evidenced in this skill's sources, and a plausible-looking recipe for a
code-execution path is worse than none. Read the tool's own current documentation, and treat anything
generated from memory about update feeds as unverified.
