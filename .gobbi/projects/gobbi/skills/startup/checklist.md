# Startup — Evaluation Coverage Register

> **Mode: evaluation coverage register.** Purpose — grade one completed startup baseline set against the
> discriminations the scenario set owns. Owner — the startup evaluation adapter (`evaluation.md`). Consumer —
> the two fresh P6.5 evaluators (one Claude, one Codex). This file is the SOURCE and ships with every box
> UNCHECKED; each run works a FRESH FILLED COPY (never the source). At Stage 0 the evaluator copies this file
> to `sessions/{date}-{session-id}/startup/working/evaluation/iter{n}/{system}/checklist.md` — the 9th
> evaluation-output file, alongside the seven per-perspective files + `overall.md`. A run that mutates the
> source corrupts every later run (CR-1).
>
> **Run-level use-style: `do-confirm` (single).** An evaluation coverage register has no runtime pause point,
> so it declares ONE run-level use-style — read back to confirm each item against inspected evidence (CR-1).
> The filled copy records the source version, the system, the iteration, and the frozen target set.
>
> **Three terminals only — nothing softer.** Every row closes to EXACTLY ONE of `PASS` / `FAIL:<finding-id>` /
> `n/a:<property>` (CR-2). There is NO `recorded-open`, `deferred`, `waived`, or `CONSIDERED` terminal in this
> register, and NO advisory item — a coverage register carries gate and required items only (CR-2).
> `PASS` — the pass condition is verified true with the named evidence. `FAIL:<finding-id>` — verified false;
> cite the finding. `n/a:<property>` — the applicability predicate is verified FALSE with inspected evidence;
> name the property (a bare property label without inspected evidence is not `n/a` — an applicable item can
> never be relabelled `n/a` to dodge the gate, CR-6).
>
> **`criticality` — GATE(killer) vs REQUIRED.** Each item declares one criticality in `[...]`. An item is
> **GATE** (killer) when its miss is the most costly or irreversible — a load-bearing acceptance claim, or a
> safety / data-loss / trust-boundary / secret check; it is **REQUIRED** otherwise. With no runtime pause
> point, every GATE's stop action reads as *open a blocking finding*; each GATE also names the concrete harm
> its miss causes (CR-7). Both GATE and REQUIRED are acceptance-bearing (CR-5) — no obligation-derived check is
> ever demoted to advisory (SA-4).
>
> **Two gates — coverage-closure is NOT acceptance (CR-3).** *Coverage-closure*: every applicable gate/required
> row has one of the three terminals — the register has been fully worked. *Acceptance* is the separate,
> stronger claim: EVERY applicable gate and required item resolves `PASS`. A single `FAIL:<finding-id>` on any
> applicable gate or required item is coverage-closed but NOT accepted and blocks P7. Never fold the two.
>
> **Acceptance floor (MIG-7).** Any applicable failed gate or required check blocks P7. An underlying
> load-bearing claim the target left **recorded-open** in its own ledger is NOT a pass here: it maps to a
> `FAIL:<finding-id>` evidence check and drives ≥REVISE — ownership does not excuse it, `recorded-open` is the
> target's coverage, not this register's acceptance. Reserve `n/a:<property>` for an inspected FALSE
> applicability predicate only.
>
> **Stable IDs + split policy.** Every item keeps a stable ID `STARTUP-{PERSPECTIVE}-SCENARIO-{NN}-CHECK-{NN}`.
> Where a legacy check bundled two or more independently falsifiable claims, it is split LOSSLESSLY: the core
> atomic claim keeps the bare legacy ID, and each carved-out sibling takes the legacy ID plus a `-S{NN}` suffix
> (`-S01`, `-S02`, … in source order). The union of a core and its siblings is exactly the legacy check's
> meaning; no other sibling form is legal.
>
> **Source of the discriminations — pointer, not restatement.** The family / case taxonomy, the ten-category
> coverage register, the lenses, and the adversarial cases these items discriminate all live in the sibling
> `scenario.md`; the procedure lives in `evaluation.md`. This register mirrors each family's **obligations**
> (`O-…`) BY REFERENCE and does NOT restate the scenario taxonomy (I8). The set → family grouping below is the
> traceability scaffold imported from `scenario.md § Family → set assignment table`, not a second copy of it.
>
> **Per-item field contract (CR-5).** Each item carries its stable ID · its set + family group · one
> criticality · one atomic binary claim · an explicit `pass condition` · an `applies` (applicability)
> declaration · a named `evidence` method/source · an `on-fail` route (a GATE's route is its consequence + stop
> action) · a source trace (`src:` the obligation + scenario family). The `- [ ]` box is the resolution slot.
