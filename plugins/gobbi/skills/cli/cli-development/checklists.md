# CLI Development Checklist

This reusable unchecked source evaluates one coordination run governed by
[`cli-development`](SKILL.md), frozen for this source at SHA-256
`70c32fba3096389c5abb9d0f500b811a15edbd181b2ed89ee0e247b2add3891b`. Its stable owner prefix is
`CLIDEV`.

The subject is an exact scoped change across its applicable CLI product results, TypeScript mechanism results,
and consumer evidence. Release judgment, action authority, action-result handback, post-release observation,
and release maintenance apply only when the accepted scope triggers Release.
Specialist policy, implementation, type checking, building, testing, packaging, delivery, publication,
installation, rollout, rollback, forward-fix execution, credentials, and formal Evaluation remain outside
this source. Every condition is unchecked and contains no answer, score, remediation, or verdict.

## Lifecycle Categories

### Design lifecycle

- **Coordination subject and activation:** bind one outcome, scope, completion claim, excluded paths, owners,
  identities, evidence needs, authority boundaries, and the direct-owner bypass.
- **Owner and dependency model:** assign each decision, fact, mechanism, evidence, artifact, consumer,
  judgment, action, observation, and maintenance result to one owner and dependency chain.
- **Identity and authority separation:** keep package and direct subjects separate and distinguish release
  policy, readiness, authority, action, verification, and observation.
- **Blocker and handoff design:** define safe retained state, first unproved action, exact resume condition,
  cold-reader context, and complete or recoverable terminal states.

### Development lifecycle

- **Accepted-input reconciliation:** assemble current results from each applicable product owner for the same
  subject, and require early Release policy only when Release is triggered.
- **Realization and evidence routing:** route TypeScript implementation, typing, toolchain, testing, package,
  and direct-delivery obligations without absorbing them.
- **Result reconciliation and invalidation:** accept exact owner records, detect contradictions, reopen the
  earliest owner, and mark only affected dependents stale.
- **Release-bound readiness and action handoff:** when Release is triggered, preserve per-row readiness,
  point-of-action authority, factual action handback, exact verification, failure, and recovery as separate
  states.
- **Observation and maintenance:** bind post-action evidence, new scoped changes, support repair, deprecation,
  and retirement to current exact subjects and owners.

### Product lifecycle

- **Supported consumer outcome:** preserve one complete, honest state for each promised tuple and delivery
  identity from accepted change through support judgment.
- **Acquisition and action boundary:** let package and direct consumers progress independently through cold
  handoff, action, verification, and recovery.
- **Failure and resumed use:** retain authoritative state, exact recovery ownership, and independently
  resumable context across contradiction, missing evidence, interrupted action, and post-release failure.
- **Evolution and exit:** coordinate maintenance, deprecation, replacement, support closure, and retirement
  without silently changing unaffected command or delivery rows.

    - `CLIDEV-SC-DEVELOP-ACTION-01` — The factual action result remains separate from readiness.
  - A release-bound action fails or leaves partial state
    - `CLIDEV-SC-DEVELOP-ACTION-02` — Recovery returns to the action owner with retained evidence and state.
  - A release-bound action is reported successful without exact consumer verification
    - `CLIDEV-SC-DEVELOP-VERIFY-01` — The row remains unverified.
- Observation and maintenance
  - Verified action enters bounded observation
    - `CLIDEV-SC-DEVELOP-OBSERVE-01` — Observation uses accepted sources, subject, owner, window, and limits.
  - Report names another version or tuple
    - `CLIDEV-SC-DEVELOP-OBSERVE-02` — Nearby observation is a lead rather than current evidence.
  - A maintenance request changes several owners
    - `CLIDEV-SC-DEVELOP-MAINTAIN-01` — The new subject reuses only owner-proved unaffected results.
  - One supported form enters deprecation
    - `CLIDEV-SC-DEVELOP-DEPRECATE-01` — Deprecation reopens its exact owners and preserves unaffected forms.

### Product lifecycle

- Supported consumer outcome
  - Package-only product
    - `CLIDEV-SC-PRODUCT-PACKAGE-01` — Package support reaches one exact installed-consumer state without a direct obligation.
  - Standalone-only product
    - `CLIDEV-SC-PRODUCT-DIRECT-01` — Direct support reaches one exact target-consumer state without a package obligation.
  - Hybrid product
    - `CLIDEV-SC-PRODUCT-HYBRID-01` — Both delivery rows reach independent states under one command contract.
  - A promised row is omitted from the summary
    - `CLIDEV-SC-PRODUCT-OMISSION-01` — In-scope work cannot complete through silent scope reduction.
- Acquisition and action boundary
  - Package publication is authorized
    - `CLIDEV-SC-PRODUCT-ACTION-01` — Package action and verification affect only the exact package row.
  - Direct installation remains unauthorized
    - `CLIDEV-SC-PRODUCT-HANDOFF-01` — The direct row remains safely handed off while package work progresses.
  - Prior authority is replayed for a new artifact
    - `CLIDEV-SC-PRODUCT-AUTHORITY-01` — Changed action identity requires new current authority.
- Failure and resumed use
  - Exact target environment is unavailable
    - `CLIDEV-SC-PRODUCT-BLOCKER-01` — Candidate and unaffected rows remain safe while target evidence blocks.
  - An external action is interrupted
    - `CLIDEV-SC-PRODUCT-RECOVERY-01` — Action-result handback preserves before, after, retained, and uncertain states.
  - Post-release evidence contradicts support
    - `CLIDEV-SC-PRODUCT-INCIDENT-01` — Support reopens from the earliest owner without borrowing another row.
- Evolution and exit
  - An additive semantic change is maintained
    - `CLIDEV-SC-PRODUCT-MAINTAIN-01` — Current evidence follows the new subject or remains explicitly historical.
  - Standalone is deprecated while package stays supported
    - `CLIDEV-SC-PRODUCT-DEPRECATE-01` — Replacement, window, recovery, and support stay form-specific.
  - One delivery form retires
    - `CLIDEV-SC-PRODUCT-RETIRE-01` — Obtainability, installed state, data, cessation, recovery, and final support are explicit.
  - Command semantics retire with the delivery form
    - `CLIDEV-SC-PRODUCT-RETIRE-02` — Architecture and Release reopen separately and all affected dependents stale.
